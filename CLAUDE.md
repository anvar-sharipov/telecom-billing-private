# PyView — правила работы (СЕРЬЁЗНЫЙ ПРОДАКШЕН-ПРОЕКТ)

Это не учебный проект. PyView — биллинговая система, реально используемая
бухгалтерами и кассирами. Ошибки в коде начислений/платежей — это реальные
деньги реальных абонентов. Действовать аккуратно, ничего не менять "на
глаз", при сомнениях — спрашивать пользователя.

## 1. Что это за проект

"PyView" — Django-биллинг, написанный пользователем (Анвар) самостоятельно.
Изначально — страховка/сверочный инструмент для основной системы
"lanbilling". Часть данных бралась из lanbilling (кассиры — платежи,
бухгалтера — начисления, "станция" — звонки), часть вводилась вручную
(имена, договора, номера, адреса).

**Главная текущая задача**: предприятие переходит с lanbilling на
собственную систему "milli billing". Новая система отдаёт Excel-выгрузки
с ДРУГИМИ названиями и порядком колонок. Код парсинга сейчас жёстко
завязан на формат lanbilling — его нужно переписать под milli billing,
по возможности не ломая логику расчётов ниже по коду (сохранить контракт
данных после парсинга).

Где смотреть код импорта/парсинга (xlsx/csv/dbf):
- `telekom/views2/MATB/xlsx/importXlsx/importXlsx.py`
- `telekom/views2/MATB/DBF/...`
- `telekom/views2/MATB/pays_from_billing/...`
- вообще везде в `telekom/views2/MATB/**`

Перед переписыванием парсинга — нужен реальный пример файла выгрузки
milli billing от пользователя, не гадать формат.

  Откат: `git reset --hard 00d4553a267895ffdb421b1522730e178e85960c`,
  затем `httpd -k restart`

Процесс деплоя:
1. Правки кода на ПК (эта папка) → `git add` / `commit` / `push`
2. На сервере: `git pull`
   - если были миграции моделей — **только `migrate`** на сервере, НЕ
     `makemigrations` (makemigrations делается один раз на ПК, файл
     миграции коммитится вместе с кодом)
   - если менялся Python-код (views/models/urls) — **обязательно**
     `httpd -k restart` (mod_wsgi embedded-режим, код кешируется в
     памяти процесса Apache)
   - если менялись только шаблоны/статика — рестарт не нужен
     (DEBUG=True, шаблоны читаются с диска каждый раз)
- Конфликт git pull с локальными изменениями на сервере: сначала
  `git diff <файл>`, чтобы понять что там, и только потом решать —
  `git checkout -- <файл>` (отбросить) или `git stash` (сохранить).

**ОСТОРОЖНО с `httpd -k restart` в рабочее время**: на Windows graceful-
рестарт ненадёжен, активные запросы обычно просто обрываются. В коде
начислений (`telekom/views2/MATB/NachislitWruchnuyu/*`) используется
`transaction.atomic()` — PostgreSQL откатит незакоммиченную транзакцию
при обрыве, порчи данных не будет, но операция может остаться
"недоделанной" (часть цикла закоммитилась, часть нет). Предупреждать
бухгалтеров/кассиров перед рестартом либо делать его в нерабочее время.
Celery в проекте есть (`Dashoguz_telekom/celery.py`), но для начислений
сейчас НЕ используется — задачи выполняются синхронно прямо во view.

## 4. Apache/HTTPS (на сервере, справочно)

- Самоподписанный сертификат: `C:\Apache24\conf\ssl\server.crt`/`server.key`
- `WSGIScriptAlias`, `Alias /static`, `Alias /media` и их `<Directory>`
  блоки продублированы внутри `<VirtualHost _default_:443>` в
  httpd-ssl.conf (иначе HTTPS их не видит).
- `WSGIPythonPath` НАОБОРОТ **нельзя** дублировать внутри VirtualHost —
  mod_wsgi ругается "cannot occur within VirtualHost", должен быть один
  раз, глобально.
- HTTP→HTTPS редирект настроен и работает.
- Копии итоговых конфигов: `C:\Users\Anvar\Desktop\TELECOM\httpd_corrected.conf`,
  `httpd-ssl_corrected.conf`.

## 5. Общие правила поведения в этом проекте

- Не предлагать venv — решение осознанное, не менять.
- Не трогать старый тестовый проект на ПК (бэкап, оставлен нарочно).
- `.gitignore` уже настроен правильно (закрывает `__pycache__`, `.env`,
  `db.sqlite3`, `*.log`, `/static/`, `venv/env/ENV`, `converters/`,
  `.history/`, `media/`, `check_edara.xlsx`) — не менять без причины.
- Перед миграциями моделей — предупреждать, что `makemigrations` делается
  только на ПК, а на сервере только `migrate`.
- Любые изменения в коде начислений/платежей — особая осторожность:
  реальные деньги реальных людей. При правках парсинга Excel сохранять
  структуру данных, которую ожидает код расчётов ниже.
- При сомнениях в формате новых данных milli billing — спрашивать
  пользователя, не додумывать формат самостоятельно.
- **Git — ВСЕ команды (`git add`, `git commit`, `git push`, `git pull`,
  `git checkout`, `git stash` и т.д.) выполняет ТОЛЬКО пользователь сам.**
  Не выполнять их самостоятельно, даже если попросили что-то "закоммитить"
  мимоходом — просто сказать пользователю, что нужно сделать, и он сделает
  это сам.
- **pip install / установка любых пакетов — ТОЛЬКО пользователь сам.**
  Если для работы нужен новый пакет — не устанавливать его самостоятельно,
  а сказать пользователю какой пакет нужен и попросить установить.
